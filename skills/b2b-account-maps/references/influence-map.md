## 購買役割

B2B ソフトウェアの購買は個人ではなく合議で決まる。肩書ではなく、**この案件で
果たす機能**で分類する。同じ人が 2 役を兼ねることもある。

| 役割 | 何をする人か | 見分け方 |
|---|---|---|
| 決裁 | 予算を最終的に承認する | 「私が決める」ではなく「私が承認する」と言う |
| 推進 | 社内で提案を運ぶ。当方の代理人 | こちらが居ない会議で名前を出してくれる |
| 評価 | 技術・機能の可否を判断する | 要件表を持っている |
| 利用 | 導入後に日々使う部門 | 現状の不便を具体的に語れる |
| 門番 | 手続・条件で通す/止める（購買・法務） | 中身より条件と前例を問う |
| 反対 | 現状維持または他案を推す | 質問が反証に寄る。現行ベンダーの担当を含む |

**推進役がいない案件は進まない。** 推進役が特定できないなら、それ自体が最大の
未確認事項として `discovery-gaps` に出す。

## 2 軸の置き方

- **縦＝影響力**: 過去の決裁で実際に効いたか。役職の高さではない。決裁者でも
  現場の反対を覆せないなら影響力は中位に置く。
- **横＝賛否**: この提案に対する立場。当方への好意ではない。

座標は 0〜1 の相対値。両方について**根拠を言えること**が条件で、言えない位置は
置かずに未確認として扱う。

バブルは直径 0.95in。近い座標は重なってラベルが読めなくなる（`--dry-run` の図版
監査が `Text is hidden behind a shape drawn later` で止める）。同じ位置になる
関与者は 1 つにまとめるか、詳細を `buying-committee` の表に逃がす。

ラベルは 6 字まで。氏名・肩書の詳細は表側に置く。

## 発言からスタンスを読む

| 発言 | 読み |
|---|---|
| 「うちの場合はどうなりますか」 | 自分ごと化。支持寄り |
| 「他社さんはどうしていますか」 | 比較段階。中立 |
| 「現行でも困っていないのですが」 | 現状維持バイアス。反対寄り |
| 「稟議に上げるので資料を」 | 推進役の可能性が高い |
| 「規程上その形は前例がない」 | 門番。条件の問題であって是非ではない |
| 沈黙・欠席が続く | 中立ではない。優先度が低いか、反対を表明していない |

最後の行が重要で、**沈黙を中立として置かない**。情報が無いことは
`discovery-map` 側の `missing` として扱う。

## よくある誤り

- **営業の期待を賛否に書く。** 「良い感触だった」は発言ではない。
- **組織図をそのまま影響力にする。** 部長より現場の主任が効く領域はある。
- **反対者を載せない。** 見えている反対は扱える。載せないと対策が立たない。
- **一度描いて更新しない。** 面談のたびに位置は動く。日付を出典行に必ず書く。
- **顧客に見せる。** 個人の賛否を記録した内部資料であり、共有物ではない。

## 決裁ラインとの使い分け

`influence-map` は**人の重み**、`decision-structure` は**承認の順路**を示す。
止まっている案件では両方を並べると、影響力のある支持者が承認経路の外にいる、
といった構造が見える。

金額により経路が変わる場合は、想定金額での経路であることを出典行に書く。
