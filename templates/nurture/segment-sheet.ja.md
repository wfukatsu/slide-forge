# セグメント定義 — <Segment No.>

| 項目 | 値 |
|---|---|
| Segment No. | 例: `AWS #010` / `Azure #004` / `共通 #002` / `HLF #002` |
| 製品 | ScalarDB / ScalarDL / ScalarDB + ScalarDL |
| Epic（何をしようとしている人か） | |
| Cloud Service | AWS / Azure / Google Cloud / オンプレミス / 未定 |
| 優先度 | 高 / 中 / 低（判断根拠: ） |
| オーナー | |
| 作成日 / 最終更新 | |

**採番規則** — `<Cloud または製品略号> #<3 桁連番>`。クラウドを問わないものは `共通 #NNN`。
**既存の番号を再利用しない。** 元シートには `AWS #009` の重複があり、混乱の元になっている
（`nurture-map.ja.md` §7-2）。新規採番前に既存一覧を確認する。

## 1. セグメントの抱える状況

**買い手の状況を、買い手の言葉で。** 「ScalarDB を必要としている人」ではなく、
「何をしていて、何に困っているか」を書く。

```
（3〜5 行。技術選定の経緯 → 今できていること → 出てきた不都合、の順で書くと
  そのままナーチャリング 0 のストーリーになる）
```

### 到達手段と配信の前提

**手段ごとに、同意の根拠を書く。**空欄のまま配信しない
（論点は `nurture-map.ja.md` §8。法的判断は法務に確認する）。

チャネルは `nurture-map.ja.md` §1 の 5 つに揃えてある。
このセグメントで使わないものは「使わない」と書く。

| チャネル | このセグメントで使うか | 同意の根拠（オプトイン / 名刺交換等の例外 / 該当なし） | 配信停止の導線 | 確認済み |
|---|---|---|---|:-:|
| メール（MA ツール） | 使う / 使わない | | | ☐ |
| ウェビナー・セミナー | | | | ☐ |
| オウンドメディア・技術ブログ | | （プル。配信ではない） | — | ☐ |
| コミュニティ・SNS・パートナー経由 | | 提供元の同意範囲: | | ☐ |
| マーケティングイベント・講演（登壇） | | | | ☐ |

- **同意記録・配信停止記録はここに書かない。** 個人に紐づくため MA / CRM 側に持つ
- 対象に海外リードを含める場合は、日本の要件で通ると判断しない（`nurture-map.ja.md` §8）
