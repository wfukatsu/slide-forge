# `templates/sales/products/` — 製品別ヒアリング補遺

ヒアリングシート本体（[`../hearing-sheet.ja.md`](../hearing-sheet.ja.md)）は
**製品に依存しない**。顧客の事実を聞くだけで、製品名・バージョン・エディション・
価格の話は一切持たない。

製品ごとの判定はこのディレクトリの補遺が持つ。**製品が増えたらファイルを 1 つ足す。
本体は変更しない。**

| ファイル | 対象 |
|---|---|
| `scalar.ja.md` | ScalarDB / ScalarDL / ScalarDB Analytics |
| `_skeleton.ja.md` | 新しい製品の補遺を起こすときの雛形 |

## 分担の規則

この 2 つを混ぜない。混ぜると製品が増えたときに本体が壊れる。

| | ヒアリングシート本体 | 製品補遺 |
|---|---|---|
| 書くもの | **顧客の事実**（何を使っているか、どれだけあるか、何を求めているか） | **製品の合否基準**（その事実で提案できるか） |
| 主語 | 顧客 | 自社製品 |
| 例 | 「基幹 DB は Oracle 19c」 | 「Oracle は ANY 系権限が必要 → 付与可否を要確認」 |
| 陳腐化 | しない | する（バージョン・エディション・価格） |
| 顧客に見せるか | 見せられる（質問集として） | **見せない**（社内判定用） |

聞く内容が製品固有になりそうなときは、**一段抽象化して本体に置く**。

- ✗ 本体に「Kubernetes は 1.32〜1.35 か」→ ✓ 本体は「コンテナ基盤とそのバージョン」、
  補遺が「1.32〜1.35 以外は要確認」
- ✗ 本体に「Premium が必要か」→ ✓ 本体は「暗号化・きめ細かなアクセス制御の要否」、
  補遺が「暗号化・ABAC は Premium」

## 補遺の節構成（固定）

`scalar-deal-intake` がどの製品でも同じ順で読めるよう、**節 ID A〜F を必ずこの順で持つ**。
該当が無い節は「該当なし」と書いて残す。**節を削らない。**

| 節 | 中身 | 本体のどこを入力にするか |
|---|---|---|
| A | 課題カテゴリの判定（この製品が解ける課題の型） | §1, §6 |
| B | 適用可否チェック（提案してはいけない構成・要注意の構成） | §4.2 |
| C | 技術前提の合否（動作要件・権限・バージョン） | §4.1, §4.2 |
| D | サイジング → 構成（数量・環境の決定） | §5 |
| E | エディション・機能の要否（価格の分岐） | §4.1, §6, §11 |
| F | 判定サマリ（提案する / 条件付き / 提案しない） | 上の A〜E |

## 使い方

```bash
mkdir -p accounts/<AE 名>/<顧客名>/stages
cp templates/sales/hearing-sheet.ja.md        accounts/<AE 名>/<顧客名>/stages/hearing-sheet.md
cp templates/sales/products/scalar.ja.md      accounts/<AE 名>/<顧客名>/stages/product-fit-scalar.md
```

本体 §1 のヘッダに、使った補遺のファイル名を書く。複数製品を並行検討する場合は
補遺を複数コピーし、本体 §1 にそれぞれの判定を並べる。

## 新しい製品を足すとき

1. `_skeleton.ja.md` をコピーして `<product>.ja.md` にする
2. 節 A〜F を埋める。**事実の出典（製品ドキュメント・価格表）を各節の冒頭に書く**
3. 鮮度の規則を書く（例: 価格とエディションは 3 ヶ月ルール）
4. この README の表に 1 行足す
5. 本体は変更しない。本体に無い顧客の事実が必要になった場合だけ、
   **製品名を出さない形で**本体 §4.2 か §5 に行を足す
