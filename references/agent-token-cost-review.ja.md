# エージェント／スキルのトークンコスト改善レビュー

## 目的

slide-forge のエージェント指示とスキル定義を対象に、LLM の入力コンテキストや
画像入力を大きくする構造を特定し、品質と安全性を維持したままトークンコストを
削減するための改善事項を整理する。

調査対象は `AGENTS.md`、`.agents/skills/forge/SKILL.md`、`skills/*/SKILL.md`、
およびスキルから参照される `references/*.md` とする。

> **注意:** 以下のトークン数はファイルサイズ、語数、日本語比率から求めた概算で
> あり、使用モデルやトークナイザーによって変動する。

## エグゼクティブサマリー

最大のコスト要因は次の4点である。

1. `google-slides-template/SKILL.md` が625行・約42KBあり、単純な操作でも全文読込が必要
2. `forge`、生成スキル、`slide-qa` の間でインテイク・検証・QA・報告手順が重複
3. 12枚超でのファンアウトにより、サブエージェントが設計資料を繰り返し読み込む
4. サムネイルQAがページ数と修正回数に比例して画像トークンを消費する

優先度の高い対策は、`google-slides-template` の縮小、`forge` の純粋な
オーケストレーター化、ファンアウト条件の見直しである。この3点により、標準的な
デッキ生成の指示・参照コストを概ね30〜50%削減できる可能性がある。

## 調査結果

### スキル本体の規模

| 順位 | スキル | 行数 | バイト数 | 評価 |
|---:|---|---:|---:|---|
| 1 | `google-slides-template` | 625 | 42,164 | 突出して大きい |
| 2 | `scalar-account-planning-session` | 372 | 17,683 | 下位スキルと大型referenceも参照 |
| 3 | `google-slides` | 203 | 13,056 | 大型referenceの入口が多い |
| 4 | `scalar-account-plan` | 310 | 12,945 | 営業ルールと生成手順が混在 |
| 5 | `scalar-product-slides` | 220 | 12,197 | 調査手順と生成手順が混在 |
| 6 | `scalar-proposal-slides` | 191 | 11,573 | 複数の共通知識を再説明 |
| 7 | `scalar-ae-materials` | 217 | 10,382 | 台帳、提案、QAのルールが重複 |
| 8 | `template-forge` | 190 | 9,769 | テンプレート作成知識を広く保持 |

`AGENTS.md` は該当スキルの `SKILL.md` を最後まで読むよう要求している。そのため、
スキル本体に置かれた索引、背景説明、サンプルカタログも毎回の固定費になる。

### 典型的な読込チェーン

登録テンプレートを使った通常のデッキ生成では、概ね次の文書が読み込まれる。

```text
AGENTS.md
  └─ forge/SKILL.md
       └─ google-slides-template/SKILL.md
            ├─ interactive-intake.md
            ├─ parallel-generation.md
            ├─ validation.md
            └─ slide-qa/SKILL.md
```

図表や画像を使うと、さらに `diagrams.md`、`charts.md`、`patterns.md`、
`slide-patterns.md`、`images.md`、`api-notes.md` などが追加される。基本チェーンだけでも
概算15,000〜25,000トークンに達する可能性がある。

## 改善指摘

### P0-1: `google-slides-template/SKILL.md` を実行手順に限定する

#### 問題

同ファイルには次の異なる役割が同居している。

- 実行ワークフロー
- コマンドのQuick Reference
- 描画方式のカタログ
- API制約とデザイン原則
- 全スクリプト、reference、サンプルの一覧
- 並列生成とQAの要約

Quick Reference とファイル一覧には重複もある。単純なテンプレート選択や1枚修正でも
約42KBすべてを読むことになり、概算8,000〜11,000トークンの固定費になる。

#### 改善案

本体を150〜200行程度に縮小し、以下だけを残す。

1. 適用条件と非適用条件
2. 既存デッキ編集時のスナップショット規則
3. インテイクとアウトライン承認ゲート
4. Spec作成、dry-run、生成の最小手順
5. `slide-qa` への委譲
6. 最終報告の必須項目

コマンド一覧、描画API、カタログ、API上の落とし穴は用途別referenceへ移す。
referenceは「必要なときだけ読む」という条件を明記する。

#### 期待効果

- 通常呼出しの固定コンテキストを数千トークン削減
- 重要な安全規則と承認ゲートが長文に埋もれにくくなる
- 重複説明の更新漏れを減らせる

### P0-2: `forge` をルーター兼状態機械に限定する

#### 問題

`forge` は下位スキルを選択した後も、インテイク、アウトライン承認、dry-run、生成、
QA、PPTX、Spreadsheet、最終報告を再説明している。これらは下位スキルにも記載され、
同じ作業で複数回読み込まれる。

#### 改善案

`forge` の責務を次に限定する。

```text
スキル選択
  → 共通インテイクの開始
  → アウトライン承認状態の確認
  → 選択した生成スキルへ委譲
  → 任意成果物のスキルへ委譲
  → 完了条件の確認
```

具体的なコマンド、QAチェックリスト、再生成規則は所有スキルだけに置く。
共通ルールが必要なら短い `workflow-contract.md` を唯一の正本として参照する。

#### 期待効果

- `forge + 下位スキル` の二重読込を削減
- 手順変更時の不整合を防止
- 各スキルの責務が明確になる

### P0-3: 12枚超の自動ファンアウトを見直す

#### 問題

`forge` は12枚超でファンアウトを要求する。一方、`parallel-generation.md` は、
サブエージェントごとにreferenceを再読込するため、並列化は主エージェントの文脈と
待ち時間を減らしても総トークンを増やすと明記している。

12〜15枚の箇条書き中心のデッキでは、分割指示、各エージェントの初期化、検証、
結果統合のコストが、単一エージェントでの連続生成を上回る可能性が高い。

#### 改善案

枚数だけでなく、次の条件でファンアウトを決める。

- 原則18〜20枚以上
- 異なる種類の複雑な図が複数ある
- ページ群を明確に独立させられる
- 画像QAにより主エージェントのコンテキストが圧迫される

12〜17枚で同一レイアウトや箇条書きが中心なら、逐次生成を既定にする。
分割時は1エージェントあたり2〜3枚を維持し、読むreferenceを最大1〜2個に制限する。

#### 期待効果

- 中規模デッキでのエージェント起動数を削減
- referenceの重複読込を削減
- 並列化が本当に有効なケースへ計算資源を集中

### P1-1: referenceを全文ではなくセクション単位でルーティングする

#### 問題

スキル内の「詳しくはこのreference」という指示だけでは、エージェントが安全側に
倒して全文を読む可能性がある。

> **2026-08 追記**: この節が挙げていた肥大化（`google-slides-api.md` 約64KB、
> `pictogram-catalog.md` 約71KB、各 Composer 15〜36KB）は解消済み。実体は
> 「大きすぎる」ではなく「現存しない API（SlideBuilder / theme.json /
> compose_*）を説明していた」ことで、prose を残して現行 API に書き直した結果、
> 3 系統で 563KB → 109KB になった。名前引きは `illustrations.py --list` /
> `list_slide_templates.py` に移し、カタログ本文を開かなくても済むようにした。

#### 改善案

referenceの参照条件と必要セクションを明示する。

```text
- 既存デッキを編集するときだけ: google-slides-api.md の「座標系」節
- コネクタを使うときだけ: diagrams.md §4、api-notes.md §1
- 画像枠を使うときだけ: images.md §2–3
- 棒グラフを使うときだけ: charts.md §Vertical bars
```

長大なカタログには先頭に短い判断用インデックスを置き、通常はインデックスだけを読む。
具体的なコンポーネントが決まった後に該当セクションだけを追加読込する。

#### 期待効果

- 図表を1種類使うだけのタスクで大型reference全体を読むことを防止
- Progressive disclosureを実際の読込単位まで落とし込める

### P1-2: QAの再検査を差分中心にする

#### 問題

サムネイル1枚は数百〜約1,000トークンを消費し得る。20枚を全件検査すると画像だけで
数千〜20,000トークン規模となり、不具合修正のたびに全ページを再検査すると繰り返し
発生する。

#### 改善案

初回QAは全ページを対象とし、修正後は次だけを再検査する。

- 修正したページ
- 修正ページの前後1ページ
- 共通レイアウトを変更した場合、そのレイアウトを使うページ
- マスターやテーマを変更した場合のみ全ページ

また、画像入力前に可能なチェックを自動化する。

- text overflowの推定
- safe area違反
- オブジェクト境界の重なり
- コントラスト
- コネクタ端点
- ページ番号の有無

自動検証で候補を絞った後も、初回の目視QA自体は省略しない。

#### 期待効果

- 修正ループ時の画像トークンを大幅に削減
- 全ページQAという品質基準を維持

### P1-3: Scalar系の共通ルールを一元化する

#### 問題

`scalar-product-slides`、`scalar-proposal-slides`、`scalar-account-plan`、
`scalar-account-planning-session`、`scalar-ae-materials` で以下が重複する。

- 既存資料を質問前に読む
- 営業ステージやBANTの扱い
- Driveフォルダと社内／顧客向けの境界
- 調査鮮度
- アウトライン承認
- Visual QAと再生成

#### 改善案

次の共通文書を正本として切り出す。

- `scalar-workflow-contract.md`: 承認、Drive、安全、QA
- `scalar-research-policy.md`: 鮮度、出典、再調査条件
- 既存の `sales-playbook.md`: 営業ステージと判定基準

各スキル本体には、固有の成果物、入力、判断、生成コマンドだけを残す。

#### 期待効果

- Scalar系スキルの総量と重複を削減
- 営業ルールや安全規則の改訂漏れを防止

### P1-4: 調査エージェントの重複検索を制限する

#### 問題

`scalar-product-slides` は情報が古い場合、会社情報、製品技術、事例を並列調査する。
並列化自体は速いが、共通サイトや同じニュースを複数エージェントが読み、出典説明も
重複しやすい。

#### 改善案

- 調査対象ドメインとURL集合を親エージェントが先に分割する
- 各調査エージェントへ共通SKILL全文を渡さず、調査契約だけを渡す
- 返却形式を「事実、日付、URL、適用スライド、未確認事項」に固定する
- 前回調査との差分を優先し、変化のない基礎説明は再収集しない
- 小規模な更新では単一調査エージェントを使う

#### 期待効果

- Webページ内容と出典説明の重複を削減
- 調査結果の統合コストを低減

### P2-1: 英語版／日本語版の重複は実行時対策の後に扱う

英語版と日本語版の文書が多数存在するが、実行時に片方だけ読むなら直接のトークン
コストにはならない。同期の保守コストはあるものの、まずはスキル本体と参照ルーティングを
改善するほうが効果が高い。

将来的には、規則やコマンドを言語非依存の短い正本に置き、説明文だけを翻訳する構造を
検討する。

## 推奨する実装順序

1. `google-slides-template/SKILL.md` のQuick Referenceとファイルカタログを分離
2. `forge/SKILL.md` から下位スキルと重複する具体手順を削除
3. ファンアウト条件を「12枚超」から複雑性を含む判断へ変更
4. 長大なreferenceへセクション索引と読込条件を追加
5. QAの差分再検査ルールを `slide-qa` と `validation.md` に追加
6. Scalar系の共通ワークフローと調査ポリシーを一元化

## 改善後の目標値

| 指標 | 現状 | 目標 |
|---|---:|---:|
| `google-slides-template/SKILL.md` | 625行 / 42KB | 200行以下 / 15KB以下 |
| `forge/SKILL.md` | 87行だが下位手順を再説明 | 50〜60行のルーティング中心 |
| 中規模デッキのファンアウト | 12枚超で実行 | 原則18〜20枚以上または複雑性条件 |
| サブエージェントのreference | 1〜2文書を全文読込し得る | 1〜2セクションに限定 |
| 修正後QA | 全ページ再読込になり得る | 差分＋影響範囲中心 |

## 検証方法

改善前後で同じ代表タスクを実行し、次を比較する。

1. 初回生成までの入力トークン
2. サブエージェントを含む総入力・出力トークン
3. QA初回と修正後QAの画像入力トークン
4. 完了までの経過時間
5. dry-runエラー数と目視QA指摘数
6. 承認ゲート、安全規則、Driveルールの遵守率

代表タスクには、5枚の単純デッキ、15枚の標準提案書、25枚の図表中心デッキ、
既存デッキの1枚修正を含める。トークン削減だけでなく、品質と安全性が悪化していないことを
完了条件とする。
